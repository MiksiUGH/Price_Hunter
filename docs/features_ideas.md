## Идеи для будущего

### 1. Рекомендация аналогов

При проверке подписки, если текущее предложение недоступно или цена выросла выше порога, можно предложить пользователю аналогичные товары (другие предложения того же продукта или похожие продукты) с более выгодными условиями.

**План реализации:**
- В команде `update_favorites` после обработки подписки сделать дополнительный запрос к `Offer.objects.filter(product=check_offer.product, in_stock=True).exclude(id=check_offer.id).order_by('price')[:3]`.
- Сформировать блок в письме: «Возможно, вас заинтересуют эти предложения».
- Для межпродуктовых аналогов – использовать `normalized_name` и нечёткое сравнение, но это сложнее.

### 2. Поддержка Ozon и Яндекс.Маркета

Дописать классы `OzonParser` и `YandexMarketParser`.  
Основная сложность – антибот-защита и динамическая вёрстка. Можно использовать API, но они требуют регистрации.

### 3. Улучшение нормализации названий

Текущая нормализация удаляет стоп-слова и пунктуацию, что иногда склеивает разные товары.  
Предлагается:
- Убрать нечёткий поиск полностью, оставив только точное совпадение `normalized_name`.
- Добавить ручное объединение/разделение продуктов через админку.
- Для поиска использовать полнотекстовый индекс (PostgreSQL `tsvector`).

### 4. Web-интерфейс для управления кастомными командами

Создать страницу для администратора, где можно вручную запустить `update_all_offers` или `update_favorites` и посмотреть логи.

### 5. Поддержка телеграм-ботов

Дублировать уведомления в Telegram через Bot API.  
Настройка: пользователь вводит chat_id в профиле, выбирает способ уведомлений.

### 6. Аналитика цен

Графики изменения цены на странице продукта (на основе `PriceHistory`).  
Простой вариант: передавать данные в Chart.js.

### 7. Кэширование результатов парсинга

Использовать Django Cache (memcached/redis) для хранения результатов поиска на короткое время (например, 1 час), чтобы уменьшить количество запросов к парсеру.

### 8. Автоматическое обновление селекторов парсера

Сложная идея: мониторить изменения в DOM и отправлять уведомление администратору, если ожидаемые элементы не найдены.  
На практике проще регулярно проверять работоспособность парсера и вручную править селекторы.

### 9. Docker-контейнеризация

Создать `Dockerfile` и `docker-compose.yml` для простого развёртывания вместе с Chrome/ChromeDriver, PostgreSQL, Redis.

### 10. Многопоточность в парсерах

При обновлении большого количества URL можно использовать `concurrent.futures` для параллельных запросов (но осторожно – риск блокировки со стороны маркетплейса).

Медленный поиск по запросу — главное узкое место, потому что парсер запускает браузер, загружает страницу WB, сортирует, фильтрует, скроллит. Даже на мощном сервере это занимает 5–10 секунд, на слабом — до 30 секунд и больше. Вот несколько способов ускорить процесс (от простых к сложным).

## 1. Кэширование результатов поиска (самое эффективное)

**Идея:** сохранять результаты поиска (с учётом фильтров) в кэш (например, Redis, Memcached, или даже в базу данных) на ограниченное время (например, 30–60 минут). При повторном запросе того же самого `query` с теми же фильтрами отдавать данные из кэша, не запуская парсер.

**Как реализовать:**
- Установить `django.core.cache.backends.locmem` (встроенный кэш в памяти) или подключить Redis.
- В `query_search` перед вызовом парсера генерировать ключ: `f"search:{normalized_query}:{price_min}:{price_max}:{delivery_days}:{sorted_marketplaces}"`.
- Проверять наличие в кэше. Если есть — возвращать HTML-фрагмент (или готовые данные). Если нет — запускать парсер и сохранять результат в кэш на, скажем, 3600 секунд.

**Плюсы:** кардинально снижает нагрузку для популярных запросов.  
**Минусы:** требует настройки кэша, при изменении данных (появление новых товаров) пользователь не увидит их до истечения кэша.

## 2. Асинхронный поиск (фоновые задачи)

**Идея:** не заставлять пользователя ждать, пока парсер отработает. При поиске сразу отдавать страницу с сообщением «Идёт поиск», а в фоне запускать задачу (Celery, Redis Queue, или просто поток). Когда данные готовы — отправлять их через WebSocket или AJAX-запрос (например, каждые 3 секунды проверять, завершилась ли задача).

**Реализация (упрощённо):**
- При поиске создавать уникальный идентификатор задачи (task_id) и запускать `search_task.apply_async(...)` через Celery.
- Возвращать пользователю страницу с лоадером и JS-кодом, который каждые 2 секунды отправляет запрос на `/hunter/search_status/<task_id>/`.
- Когда задача завершена — возвращает результат и отрисовывает карточки.

**Плюсы:** пользователь не висит на одном запросе, сервер не блокируется.  
**Минусы:** сложность реализации (нужен брокер сообщений – Redis/RabbitMQ), дополнительные процессы.

## 3. Оптимизация самого парсера

**Что уже можно улучшить без кардинальных изменений:**

- **Уменьшить `answer_cnt` для веб-поиска.** В `query_search` вызывается `min(answer_cnt, 10)`. Можно временно снизить до 5 или 3. Быстрее парсится.
- **Удалить ненужные ожидания.** Вместо `time.sleep(2)` использовать явные ожидания `WebDriverWait` с меньшим таймаутом. Например, после клика по сортировке не ждать 2 секунды, а ждать появления карточек.
- **Переиспользовать один драйвер на несколько запросов.** Сейчас при каждом поиске создаётся новый драйвер. Можно создать пул драйверов, которые переиспользуются (например, 1–2 драйвера, которые живут постоянно). Но это сложнее и требует синхронизации.
- **Убрать сортировку и фильтрацию, если они не нужны.** По умолчанию можно не сортировать по цене, а отдавать как есть (время сортировки — несколько секунд). Фильтр по цене тоже не всегда нужен.
- **Использовать мобильную версию сайта WB** (m.wildberries.ru) — она легче, быстрее загружается, содержит те же данные.

## 4. Переход на альтернативный метод получения данных (без Selenium)

Wildberries (и другие маркетплейсы) часто загружают товары через AJAX-запросы, которые возвращают JSON. Можно эти запросы повторять напрямую через `requests`, что будет в десятки раз быстрее Selenium. Но требуется анализ сетевого трафика (DevTools → Network → Fetch/XHR).

**Пример:**  
При поиске WB отправляет POST-запрос к `https://www.wildberries.ru/webapi/catalog/product/search/?search={query}`. Ответ — JSON с товарами. Распарсить его легче и быстрее (за 1–2 секунды). Однако такие эндпоинты могут быть защищены от ботов или требовать авторизации. Но для поиска это возможно.

**Плюсы:** скорость 1–3 секунды вместо 15–30.  
**Минусы:** придётся переписать парсер, изучать API, риск, что его заблокируют или изменят.

## 5. Поиск сначала в БД, парсер — в фоне

У вас уже реализовано: сначала ищете продукты в БД (по нормализованному имени). Если нашли достаточно (≥30), то парсер не запускаете.  
Можно увеличить это число (например, до 50) и добавить в БД записи о том, что последний раз парсили товары по запросу. Если результаты свежие (например, не старше 2–3 дней) — не перепарсить.

## 6. Предварительное «согревание» драйвера

При запуске сервера можно инициализировать один экземпляр драйвера и держать его открытым. Тогда первый поиск будет быстрее (не нужно создавать браузер). Но это может привести к утечкам памяти и блокировкам.

**Пример в `apps.py`:**
```python
from django.apps import AppConfig
from core.utils.parsers import get_driver

class CoreConfig(AppConfig):
    def ready(self):
        # Создать глобальный драйвер при старте
        import atexit
        driver = get_driver()
        atexit.register(driver.quit)
```
Но потом этот драйвер нужно переиспользовать в `WbParser` (передавать как аргумент). Это изменение архитектуры.

## Что я рекомендую сделать **прямо сейчас** (без глобального рефакторинга):

1. **Включить кэширование** (самое простое и эффективное).  
   Установите `django.core.cache.backends.locmem.LocMemCache` (работает из коробки). В `settings.py`:
   ```python
   CACHES = {
       'default': {
           'BACKEND': 'django.core.cache.backends.locmem.LocMemCache',
           'LOCATION': 'pricehunter-cache',
       }
   }
   ```
   В `query_search` перед вызовом парсера:
   ```python
   from django.core.cache import cache
   cache_key = f"search_{normalized_query}_{price_min}_{price_max}_{delivery_days}_{str(sorted(marketplaces))}"
   cached_result = cache.get(cache_key)
   if cached_result is not None:
       return render(request, 'core/partials/search_results.html', {'products': cached_result})
   ```
   После получения результатов парсинга сохраните в кэш на 1 час:
   ```python
   cache.set(cache_key, best_matches, 3600)
   ```
   Это сильно ускорит повторные поиски того же запроса.

2. **Уменьшить `answer_cnt` для веб-поиска** до 5 (вместо 10).  
   В строке `parsed = shop.search_by_query(query, min(answer_cnt, 5), ...)`.

3. **Увеличить лимит товаров из БД** (например, с 30 до 50), чтобы реже запускать парсер.

4. **Добавить в БД поле `last_searched` для запроса** – если искомый запрос парсили недавно (например, < 6 часов), не парсить снова.

Эти изменения займут 1–2 часа и дадут значительный прирост производительности. Если этого не хватит, переходите к асинхронному поиску или альтернативному API.
